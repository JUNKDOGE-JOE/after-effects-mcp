# After Effects 2024 on Windows: Compatibility Findings and Repair Guide

This document records compatibility problems reproduced with
`after-effects-mcp` v0.9.5 on After Effects 24.6.8 for Windows. It is written
both for maintainers and for coding agents such as Codex or Claude that may be
asked to diagnose or repair an AE 2024 installation.

## Tested environment

- Project tag: `v0.9.5`
- Source commit: `636d6f69ee49b06ce2c1a897d616fa19cae9aea7`
- Host: After Effects 24.6.8, Windows x64
- Native SDK declaration: AE SDK 25.6.61
- Compiler used for diagnosis: MSVC 14.44.35207
- Panel runtime: CSXS/CEP 11
- Newer AE 25 and AE 26 did not reproduce the native runtime crash on the
  same workstation.

## Executive summary

Two root causes were confirmed and one integration issue was reproduced:

1. The Windows AEX was compiled with `/MD` and loaded AE 2024's old private
   `MSVCP140.dll`. Code generated by a current VS 2022 toolset then crashed in
   `std::mutex::lock`. Building the AEX with `/MT` fixed the crash while keeping
   native IPC and all AE operations enabled.
2. CEP 11 cannot resolve CommonJS imports such as `require('node:crypto')`.
   CEP-hosted JavaScript must use bare built-in names such as
   `require('crypto')`.

The integration issue is that Codex Desktop may expose a
Microsoft Store/WindowsApps command alias that a CEP helper cannot execute.
The panel needs a stable, directly executable Codex CLI path.

Two lifecycle changes also improved pre-fix A/B builds: removing blocking
`AEGP_DeathHook` cleanup and disabling synchronous diagnostic file I/O. Those
observations were made before the `/MD` mismatch was identified, so they are
documented below as follow-up investigations rather than independent root
causes or changes that should be merged without further isolation.

## 1. Native crash caused by `/MD` and AE 2024's old C++ runtime

### Symptoms

- AE displayed `After Effects MCP Native` as the crashing plugin.
- AE sometimes reported the last recorded message as:

  ```text
  <FontServer> SetDefaultByScript:kCTSimplifiedChineseScript=>SimSun/TrueTypeFont
  ```

- The same AEX behavior was reported as working in AE 25 and AE 26.
- Disabling native IPC avoided the immediate crash, but removed required
  functionality and was therefore only useful as an A/B diagnostic.

### Crash-dump evidence

The AE Sentry minidump reported:

```text
ExceptionCode: 0xC0000005 (EXCEPTION_ACCESS_VIOLATION)
ExceptionAddress: MSVCP140.dll + 0x126A0
Caller: AeMcpNative.aex + 0x2682B
```

Relinking the same object files with `/MAP` mapped the AEX offset to the body of:

```text
std::_Mutex_base::lock
```

The loaded module list showed that `MSVCP140.dll` came from the After Effects
2024 application directory, not from the current Visual Studio runtime. The
AEX was compiled with current VS 2022 headers and `/MD`, but the host-local DLL
had an old 2019-era timestamp. The plugin therefore executed current standard
library code against AE's older private runtime.

The FontServer message was only the last normal main-thread breadcrumb. It was
not the faulting module and should not be used as evidence that the system font
is corrupt.

### Upstream fix

In `native/ae-plugin/build-windows.mjs`, change the Windows AEX compile runtime
from `/MD` to `/MT`:

```diff
- '/utf-8', '/Od', '/MD', '/GS', '/guard:cf', '/permissive-',
+ '/utf-8', '/Od', '/MT', '/GS', '/guard:cf', '/permissive-',
```

Use the same runtime choice in every official Windows build path. Do not mix
`/MD` and `/MT` object files in one AEX.

### Verification

After building, inspect the import table:

```powershell
dumpbin /imports AeMcpNative.aex |
    Select-String 'MSVCP140|VCRUNTIME140|ucrtbase'
```

For the repaired build, this command returns no matches. The test build kept
native IPC, idle dispatch, command invalidation, and AE operation execution
enabled. It started successfully, published a native endpoint, accepted panel
connections, and no longer crashed at startup.

## 2. Follow-up: AE 2024 shutdown and `AEGP_DeathHook`

### Symptoms and isolation

AE loaded and remained usable, but closing AE produced:

```text
After Effects error: crash while invoking plug-in "After Effects MCP Native"
```

The original death hook performed all of the following while AE was already
tearing down:

- stopped and joined the IPC worker;
- locked IPC/dispatcher state;
- shut down queued work;
- wrote diagnostic logs;
- destroyed `PluginState` and suite-owning objects.

A pre-`/MT` baseline with IPC and idle processing disabled still crashed on close while
the death hook was registered. The same baseline with no death-hook
registration exited through `app.quit()` with process exit code `0`.

Because these A/B builds still used `/MD`, the old runtime mismatch may also
have affected the mutex and thread-join work inside the hook. Re-test the
original death hook after applying `/MT` before changing lifecycle ownership in
upstream code.

### Conservative fallback if `/MT` does not fix shutdown

For AE 2024 on Windows, do not register `AEGP_DeathHook` if it must join
threads, acquire C++ mutexes, write files, call suites, or destroy objects that
refer to AE host state. Keep the state process-owned and let Windows reclaim it
when AfterFX terminates.

If upstream wants to retain a death hook for newer hosts, gate it by the
detected host version. An AE 2024 hook should do no more than a lock-free store
to a trivially alive atomic flag. Cleanup that can block must happen earlier,
while the panel/helper and AE suites are still valid.

Possible fallback policy, only if an `/MT` build still reproduces the shutdown
crash:

```text
AE <= 24 on Windows: no death hook; process-owned native state
AE >= 25: existing cleanup only after dedicated startup/exit testing
```

Do not treat catching C++ exceptions as sufficient protection. Access
violations and failures inside host/runtime teardown are not reliably made safe
by `try/catch`.

## 3. Follow-up: diagnostic logging on the startup critical path

### Finding

In pre-`/MT` A/B builds, `DiagnosticLog::append()` in
`native/ae-plugin/include/aemcp_native/host_platform_windows.hpp` performed
directory creation, exclusive `CreateFileW`, `LockFile`, rotation, and writes
during AEGP startup and shutdown callbacks. An A/B build with this method
disabled passed the startup stage that previously crashed. This method also
uses `std::mutex`, so the result is confounded by the confirmed dynamic-runtime
mismatch. Do not disable logging upstream solely on this evidence; first retest
the original logger in an `/MT` build.

### Recommended implementation

- Do not synchronously open or lock files from `AeMcpNativeMain`, idle/death
  lifecycle registration, or early host callbacks.
- Buffer diagnostics in memory and flush them from a known-safe worker after
  initialization, or disable file logging on AE 2024.
- Make logging lossy and non-authoritative: failure to log must never alter
  plugin initialization or callback return values.
- Do not flush diagnostics from `AEGP_DeathHook`.

The local compatibility build used a no-op Windows `append()` as a conservative
proof. Upstream can replace that with deferred logging, but should preserve the
same lifecycle constraints.

## 4. CEP 11 cannot resolve `node:` CommonJS imports

### Symptom

The panel showed:

```text
Service failure - Cannot find module 'node:crypto'
```

The service did not reach port `11488` until this was corrected.

### Root cause and fix

`plugin/host/native-aegp-client.js` runs inside AE 2024's CEP 11 Node context.
That runtime does not support the `node:` module scheme. Replace all five CEP
host imports, not only the first reported one:

```diff
- const crypto = require('node:crypto');
- const fs = require('node:fs');
- const net = require('node:net');
- const os = require('node:os');
- const path = require('node:path');
+ const crypto = require('crypto');
+ const fs = require('fs');
+ const net = require('net');
+ const os = require('os');
+ const path = require('path');
```

Bare built-in names work on both legacy CEP Node and current Node. It is not
necessary to rewrite `node:` imports in packages that execute only in the
external Node LTS sidecar; the compatibility requirement applies to code loaded
directly by CEP.

Add a packaging test that scans CEP-executed host files and rejects
`require('node:...')` and `import 'node:...'`.

## 5. Codex Desktop CLI discovery on Windows

### Symptom

The service was green at `127.0.0.1:11488`, but chat remained disabled with:

```text
Complete codex login in a terminal, or set AE_MCP_CODEX_CLI.
```

### Root cause

The command found through `PATH` pointed into the Microsoft Store
`C:\Program Files\WindowsApps\...` package. Codex Desktop could launch it as
part of its application, but the AE platform helper received `Access is
denied` when launching that path directly.

A directly executable CLI also existed under a versioned directory similar to:

```text
%LOCALAPPDATA%\OpenAI\Codex\bin\<build-id>\codex.exe
```

It returned exit code `0` for `codex login status` and reported an active
ChatGPT login.

### Recommended product behavior

1. Honor `AE_MCP_CODEX_CLI` first.
2. Reject inaccessible WindowsApps aliases during probing.
3. Search `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe`, newest valid file
   first.
4. Validate candidates with both `codex --version` and
   `codex login status`; do not accept file existence alone.
5. Persist or manage a stable launcher path, because the `<build-id>` directory
   changes when Codex Desktop updates.
6. Explain that AE must be fully restarted after changing a user environment
   variable. Restarting only the panel/helper is insufficient because they
   inherit the already-running AfterFX environment.

A local repair can set:

```text
AE_MCP_CODEX_CLI=%USERPROFILE%\.ae-mcp\bin\codex.exe
```

The installer may copy, hard-link, or atomically update that stable launcher.
Do not hardcode one build-id directory in release code.

## False leads to avoid

### FontServer/SimSun is not automatically the root cause

AE's crash dialog reports the last recorded breadcrumb, not necessarily the
faulting instruction. In this case it displayed `FontServer` and `SimSun`, but
the minidump's exception address was inside `MSVCP140.dll`, called from the AEX
mutex implementation. Different hashes for two legitimate versions of
`simsun.ttc` are also not proof of font corruption.

Do not replace or delete system fonts based only on this breadcrumb. Inspect
the minidump exception stream and loaded-module list first.

### A green HTTP service does not prove chat readiness

`/health` returning `ok: true` and port `11488` listening prove that the CEP
host service is running. Chat may still be disabled if the selected AI backend
cannot start or is not authenticated. Report these states separately in UI and
diagnostics.

## Suggested automated repair flow for Codex/Claude

When an agent is asked to repair AE 2024 compatibility, it should execute this
order and stop changing unrelated system state:

1. Confirm AE version, project tag/commit, installed AEX hash, and panel
   version.
2. Back up the installed AEX and only the panel files that will be changed.
3. Parse the newest AE minidump. Prefer exception address/module evidence over
   the crash dialog's last-message text.
4. Ensure the Windows AEX build uses `/MT`, rebuild, and verify its import table
   contains no `MSVCP140`, `VCRUNTIME140`, or `ucrtbase` dependency.
5. Keep IPC, idle dispatch, command hooks, and native execution enabled while
   testing. A build that merely disables native functionality is not a fix.
6. Re-test the original death hook and logger with `/MT`. Change them only if a
   new minidump or isolated A/B test still implicates those paths.
7. Patch CEP-hosted `node:` imports to bare built-in names and run the host
   tests.
8. Start AE, wait for the main UI, verify a new native endpoint is published,
   and verify `/health` on port `11488`.
9. Resolve a directly executable Codex CLI, validate its login state, set
   `AE_MCP_CODEX_CLI` if needed, then fully restart AE.
10. Test one read-only prompt, one additive AE mutation, and normal AE exit.
11. Confirm no new AE Sentry minidump was generated during startup, operation,
    or shutdown.

## Acceptance checklist

- [ ] AE 24.6.8 reaches the main UI without a native-plugin crash.
- [ ] `AeMcpNative.aex` does not import the host's C++ runtime DLLs.
- [ ] Native endpoint metadata is published for the current AfterFX PID.
- [ ] The panel reports `Service running - 127.0.0.1:11488`.
- [ ] The panel detects a directly executable, authenticated Codex CLI.
- [ ] A read-only project query succeeds.
- [ ] An additive operation such as creating a test composition succeeds.
- [ ] AE closes without `crash while invoking plug-in`.
- [ ] No new startup/operation/shutdown minidump is produced.

## Local validation results

The final local compatibility stack used `/MT`, retained native IPC and
dispatch, published its endpoint successfully, allowed the panel service to
run, detected the authenticated Codex backend through a stable executable
path, and was reported by the user as no longer crashing. That local build also
contained the conservative lifecycle/logging fallbacks described above, so
upstream should use the isolated verification sequence in this document rather
than treating every local diagnostic change as required. The resulting AEX
SHA-256 was:

```text
42FC1C25D72385099C8CDEC57C6CE835DC81221B3E7DDF7C40BFF65883C31777
```

This hash is diagnostic evidence for this exact local build, not a release hash
that upstream should embed or trust.
